# Teaching first, with evidence for expert help

A delegated application attempt stopped early. Its coordinator completed the
implementation, following the prior recovery policy. The owner wanted teaching,
then clarified that an expert still needed to handle genuinely difficult sections.
One failed attempt could not establish that distinction. The final engineering
story retains both superseded policies instead of describing either as permanent.

The decision begins with diagnosis. Incomplete responses, tool problems and budget
limits differ from repeated behavioral failures in usable code. Supplying factual
references, smaller assignments and concrete feedback gives the local worker a
fair chance. Multiple substantive drafts and different actual approaches provide
an evidence floor, but the assessment also needs fixed criteria, passing good and
bad controls, recurring relevant failures and stalled progress. Improving or
unknown outcomes justify more coaching. This remains a practical judgment, not a
perfect measurement of intrinsic intelligence.

Narrow implementation help follows the assessed section. Comparable local drafts
keep test inputs and surrounding code unchanged. The expert's edit preserves raw
outside bytes. Exact expected-versus-observed mutation checks prevent unrelated
changes from silently expanding authority. Completion keeps actual authorship;
old files, unchanged copies and guidance alone cannot supply implementation credit.
Automatic needed-file access remains available without repeated permission dialogs.

Independent reviews found useful failures: a checker or fixture disguised by its
file extension escaped a seal; newline normalization weakened an exact-byte claim;
varying context made drafts incomparable; unrelated writes could be absorbed into
an updated grant; comment-only changes inside interpolated expressions fooled a
lexical proxy. Each measured gap received a narrow correction. The proxy declines
uncertain expression or slash syntax, malformed quoted strings and tokenizer errors rather than claiming to prove
algorithmic difference. Adding boundary comments alone is preparation, not an
implementation attempt.

Controlled tests covered actual draft checks, qualified partial correction and
explicit authorship. A real timed-out checker printed a plausible report and then
hung; it did not justify implementation help. The interim live teaching phase saved
partial local progress rather than silently completing it, and remained incomplete.
Those outcomes do not prove model training, permanent learning, independent
reconstruction, application correctness or audible playback.

One rerun overwrote a historical receipt before backing it up. Reconstructed bytes
matched a checksum previously measured independently, but this was never relabeled
as a pre-write backup. Unique receipt names became the prevention rule. Retaining
failed reviews, old authorship and evidence limits makes progress more assessable
than treating every completed file or printed success message as a learning claim.


A later coached continuation first returned incomplete, then succeeded on a smaller
component correction. It wrote a small adapter connecting the corrected local
module to retained earlier supervisor code with explicit authorship. A pellet-count
validation mismatch blocked integration; focused local correction followed, and
the actual saved files passed graph and simulated gameplay/audio-API assertions.
Earlier application files remained exact. Budget-limited jobs and the initial
failed integration stayed in history. There was no measured difficulty grant or
new supervisor implementation takeover. Browser rendering, physical hearing and
a hosted website still require separate evidence.
