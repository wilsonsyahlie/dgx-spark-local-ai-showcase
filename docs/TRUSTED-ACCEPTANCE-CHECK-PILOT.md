# A capped pilot of supplied acceptance checks

A preliminary finish signal was observed in this single pair.

| Measure | Current workflow | Supplied checks plus directions |
| --- | ---: | ---: |
| Clean completion | 0 | 1 |
| Full independent suite | 0 | 1 |
| Case credits | 0 | 22 |
| Accepted requests | 3 | 5 |
| Defined tool failures | 0 | 0 |
| Worker seconds | 62.04 | 34.91 |

One fresh matched module pair tested an immutable prevalidated acceptance checker supplied before implementation, with explicit directions to inspect and execute it. The baseline received the current workflow. Both retained the same eight-step ceiling, output allowance, model, sampling, tools and contract. The intervention was the checker plus directions; benefit cannot be attributed to the file alone. Baseline ran first, so order was unbalanced. Neither job received coaching, retries, replacement work or old outputs.

The contract covered per-lane interval merging, first-seen lane ordering, adjacency, reserved identifiers, strict record and endpoint types, safe integer boundaries, input immutability and harmless extra fields including functions. Nineteen supplied assertion scenarios and twenty-two independent hidden cases were authored separately. Correct-reference, missing-export, wrong-export and ten targeted faulty implementations qualified both graders. The initial launch review held for absent dedicated reserved-ID fault qualification; both unchanged graders rejected that supplemental mutant before the revised freeze was approved. The source, inputs, order, limits and decision rule were frozen before inference. A clean finish required a returned report, all independent cases and proven settlement. The candidate additionally had to run the exact supplied checker successfully against its final saved implementation bytes. Later writes invalidated earlier checker success. Sandbox overwrite denial and facade protection were tested.

The cap was two one-shot jobs and sixteen accepted requests, with a six-minute cumulative worker-time cancellation threshold. Polling and owned cleanup can overrun that threshold; it is not an exact elapsed-time ceiling. Positive preliminary evidence required an additional clean finish, final-byte checker consumption and zero paired case regressions. No production adoption or larger trial was authorized.

The baseline stopped at its third request with an output-limit incomplete receipt and no saved implementation. The treatment returned in five requests, executing the supplied checker at step four and reporting at step five. Timing is descriptive: the baseline did not complete, so comparing elapsed seconds does not establish a speed gain. The treatment executed the exact supplied checker against final code: yes. The independent comparison found 0 paired case regressions and 22 improvements. All 8 accepted native requests and 30 main-lane executor settlements were freshly verified. The executor count includes twenty-seven qualification executions plus live worker checks and final grading; separate synthetic control namespaces are excluded. Production sources, state, controller, resident runtime, historical evidence and existing dirty checkouts remained unchanged.

One selected pair cannot establish statistical significance, broad coding improvement, throughput gain or production readiness. Bounded tests do not prove exhaustive correctness or the truth of every report. Correct saved artifacts with an exhausted budget remain incomplete. Ordinary application dispatch, phone interaction, scheduling and deployment were not tested. The existing worker workflow remains active. Any follow-on experiment requires its own scope.
