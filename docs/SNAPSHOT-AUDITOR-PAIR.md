Earlier algorithm-only trials suggested that trusted acceptance checks could improve worker finishing, while also exposing a test-coverage gap. The next approved step tested a more useful task shape: implement a small snapshot-auditing library inside a supplied repository with an immutable command-line driver, usage explanation and invented example inputs. It remained a synthetic snapshot schema, rather than an existing production repository repair or a live-state auditor.

The auditor reports the consistency of supplied claims. It checks typed records, supported outcomes, unique identities, generation joins, complete artifact/check manifest agreement and declared settlement. Older unresolved work cannot disappear from the report. Explicit failure and cancellation remain visible. Output uses fixed classifications, reason codes and counts, excluding copied identifiers, paths, task text, logs and error bodies. Artifact paths remain opaque data. Matching claimed hashes or settled flags never proves that actual files exist or real processes stopped.

Two fresh one-shot local jobs received identical repository seeds and the same bounded worker policy. Only the treatment received a sealed checker and directions to run it after the final library write. Both kept the same eight-step ceiling, model, output allowance, sampling and tools. The order was baseline first. Correct references, fault controls, hidden cases, old outputs and private production snapshots remained outside worker inputs. The cap was two jobs, sixteen requests and a five-minute cumulative worker-time cancellation threshold, with polling and owned cleanup overrun disclosed. No retry, coaching, replacement, live store access, deployment or automatic next trial was allowed.

Independent expected cases used different generations and manifest shapes from supplied scenarios. Both references were authored separately. Qualification covered stale and future generations, changed and omitted artifacts, failed checks, duplicates, missing execution references, unresolved older work, input mutation, reserved opaque keys and actual command-line/library agreement, including malformed and unreadable input. Ordinary clean completion required a returned worker, every independent case and positive owned settlement. Candidate qualification additionally required actual successful canonical execution bound to final code, immutable repository seed bytes, task identity, scenario count and exact executor proof. Later code or driver changes invalidated earlier success. Both clean finishes mean no comparative completion improvement.

The pair observed 2 jobs, 14 native requests and 62 main executor settlements: 55 pre-inference qualification and 7 live checks/final grades. Eighteen implementations—two correct references, fourteen targeted faults and missing/direct exports—were tested through independent cases, full typed supplied scenarios and actual canonical execution. The candidate checker contained 17 scenarios; independent grading had 49 cases per arm. Synthetic control namespaces and a standalone language-semantics probe are separate from the main executor count. Fourteen evidence-binding negatives, sixteen worker-boundary scenarios, two equal-input request captures, finite job/label/request/time fences, thirteen ownership/recovery controls, an actual watchdog, runtime drift controls, five outcome gates, twenty-one privacy controls and four review-gate controls passed. All owned work settled. Production sources, logical state, controller, resident runtime, previous frozen artifacts and dirty primary checkouts were preserved. Tested case regressions: 27; improved case credits: 0.

The measured candidate retained a direct schema contradiction: early guards rejected the arrays required by the contract. Its canonical check failed on a valid input, the file-based debug printed an invalid result, both valid hidden driver scenarios failed, and the worker exhausted its step allowance. An inline diagnostic also had a retained syntax error; a later zero-exit debug did not count as acceptance. The current workflow finished its selected tests; the candidate did not. Its 22 passing cases comprised 18 invalid-input rejections, three command-line error paths and one immutability/freshness case; none demonstrated classification of a valid snapshot.

Post-run source inspection also found an uncovered defect in both outputs: ordinary-object identity maps treated inherited property names as duplicates, although arbitrary nonempty identity strings were permitted. Reserved artifact-map keys were tested, but reserved execution/check identity names were not. The candidate’s identity defect was latent behind its array rejection, rather than a separate measured cause of the 27 regressions. This boundary was not newly executed or rescored; both outputs remain unrepaired. The passing baseline count is selected-suite qualification, not full-contract correctness. No additional worker, repair or acceptance expansion occurred.

Prelaunch review briefly raised a language-semantics concern about a regular-expression end anchor. A bounded check in the actual runtime rejected the alleged trailing-line-terminator case, so the reviewer retracted the claim. The main agent independently confirmed it. No qualified reference, case or frozen source changed for that mistaken concern. The lesson is to measure a language-specific boundary in its actual runtime before asserting a defect or editing qualified code. The original claim and correction remain retained; no failed preparation qualification was hidden.

This single baseline-first pair tests feasibility against a supplied snapshot contract, not general repository productivity, statistical significance, a causal mechanism, speed, model learning or production readiness. The checker and directions are a bundle. Passing cases are bounded, not exhaustive correctness or verification of every worker report. Claimed snapshot hashes and settlement flags are not authenticated live evidence. Credits against absent implementations are not separate diagnosed defects. Historical buggy artifacts and scores remain unchanged. Application integration, ordinary supervised dispatch, phone interaction, scheduling, restart and deployment were not tested. Any further trial or adoption requires its own scope.
