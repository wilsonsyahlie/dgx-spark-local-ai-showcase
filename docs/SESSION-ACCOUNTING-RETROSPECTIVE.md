# Recovering a verifier by preventing session-accounting growth

A media validation process failed before executing its first instruction. Read-only diagnosis found exhausted operating-system accounting capacity associated with abandoned remote-session records. Replacing content would not address that measured startup boundary.

The first repair design paired prevention with a tightly bounded cleanup. Its live eligibility check correctly stopped when previously frozen unused records disappeared. No configuration or kernel cleanup occurred. The clearing actor was unknown, and the recovery path confirmed that the original settings were still present.

A smaller successor removed all cleanup capabilities and applied only the approved prevention change. It preserved the rest of authentication behavior and the original startup content. Explicit authorization provenance connected this narrower operation to the existing approval rather than inventing a new approval.

Two independently authenticated channels preceded publication. One performed the change; the other exclusively owned guarded recovery. Each file could be restored once only if it still matched the recognized candidate. Unknown state held, and partial recovery retained read-only status within a fixed lifetime. Expiry and lost connections caused no automatic writes.

Review also caught a misleading health measure: an unchanged total can hide one newly allocated group when another disappears. Identity-aware comparisons and the process's own membership replaced that inference. Adversarial controls covered equal-count churn, replaced identities, partial publication, foreign edits, uncertain acknowledgements, concurrent recovery and expiry.

Live file and backup checks passed. Independent fresh sessions showed no new accounting groups. No cleanup or service restart was performed. A separately qualified first execution of the original verifier then ran and passed its full content checks while retaining the original attempt history.

Subsequent scheduled processing also completed new source and installed-file checks under the unchanged acceptance policy. A separate metadata-contention correction used bounded waiting only to read finalized proofs, retaining the validator and fresh file-identity checks. It did not introduce a broad retry of uncertain operations.

These results establish prevention, recovered execution and bounded natural continuation. They do not establish complete delivery, human playback or persistence through a real reboot. Broader fulfillment remained unfinished at this checkpoint. This is a retrospective engineering account, without deployment instructions or production configuration.
