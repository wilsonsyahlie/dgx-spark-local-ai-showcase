# Adding software inspection without changing the reasoning model

An assistant needed to investigate selected software using REA. The design favored a version-pinned analysis command and focused workflow instructions over adding a large tool catalog to every ordinary conversation. The extension reused an existing command interface and preserved the reasoning model.

Verification separated package installation, instruction discovery, real analysis and actual agent use. Every file from the published package matched the installed copy. A deliberately inert sample application supplied a known message channel and exposed API. Static analysis recovered their relationship; source digests and an execution sentinel checked that the sample was neither modified nor run. A missing-target case produced a structured error. A separate binary-inspection check returned assembly, which was explicitly distinguished from decompiled source.

The local assistant itself invoked the analyzer and generated the same Evidence record as the independent control. A successful installer exit would not have established that behavior. Final explanation and cleanup were treated as separate acceptance criteria.

Review improved the verification harness before the live request: preserve the first failure, observe cleanup independently and require positive closure before releasing the watchdog. Command and runtime lookup mistakes were retained in the private evidence record.

This exercise did not establish universal format support, native pseudocode recovery or runtime observation. Optional engines remained prerequisites, and static findings were not presented as proof of execution. No general speed improvement was inferred.

The reusable lesson is to add specialist capabilities at the existing interface, then verify an agent actually uses them. Package presence, tool output and a supported conclusion are distinct claims.

[REA project](https://github.com/morluto/rea). This is a retrospective engineering account, not an installation guide or deployable system description.

## Making the capability usable from an investigation tab

A later extension put target selection, questions, progress and findings in one page. The difficult part was preserving identity and truthful state: a lost response must not create another investigation, recovered commentary must not be labeled a finished answer and cancellation must prevent a worker from submitting after the page says it stopped.

Review and failure controls corrected those boundaries before backend activation. Browser checks covered duplicate clicks, late reads, refresh recovery, clarification drafts during polling, hostile-text rendering and narrow phone layouts. A browser compatibility assumption also failed on the actual connection type and was corrected using an available cryptographic random source.

The interface reused an existing local assistant. Instructions requested static inspection, but did not establish a new execution sandbox. Uploads and additional analysis engines remained outside this extension. The earlier citation error remains a limit on generated explanations. This is an interface and reliability improvement; it does not establish a faster model or universal reverse-engineering support.


The live assistant placed temporary evidence outside the requested investigation output folder. The earlier existence and overwrite protection of that temporary file were not established. This instruction-following deviation is retained: neither output confinement nor unchanged unrelated temporary files is claimed.


The real browser-created investigation returned the correct message channel, API method and transformation, with the matching Evidence record and correct root attribution. The evidence file matched the independent control. Reloading and restarting the web service preserved the original job without replay; final findings were visible at desktop and both phone widths. Target digests and the execution sentinel passed, and task/session/backend closure was positively observed. Prior conversations and settings, and existing assistant/model container definitions and process identities, were preserved.

A separate effective swap-limit check failed even though current swap usage was zero. Its onset and cause were not established because the corresponding pre-run counter was missing. The failure was retained separately from passing functional checks; this interface change did not repair that limit or establish full runtime preservation. Qualified functional acceptance is not an assertion that every platform invariant is healthy.
