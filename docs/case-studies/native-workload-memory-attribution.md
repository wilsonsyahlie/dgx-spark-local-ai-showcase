# A running model appeared to use no memory

A resource dashboard showed a running assistant using zero accelerator memory. In the same sample, the unknown-workload category contained roughly68GiB. Restoring an older engine had changed its launch signature, so the classifier no longer recognized it.

The repair tied the native entrypoint to an explicitly owned running workload and the accelerator process's full container membership. A familiar Python or model name alone was insufficient. Unknown or failed identity checks continued to leave memory unassigned, and the measured total stayed conserved.

Focused identity and alias checks passed. The actual desktop and phone-width page then showed about68GiB under the assistant, with correct controls and refresh behavior. Simulated delayed and stale reads, read failure and retry were also checked. The inference process stayed untouched while only the dashboard service restarted.

This separately authorized correction closes the display limitation recorded in the preceding restoration story. It does not claim a performance improvement, an exact accounting of all shared memory, physical phone testing or compatibility with every future engine. Observable process identity is more dependable than a single launch convention.

## Follow-up: releasing an idle desktop model

A desktop accelerator remained mostly occupied even when no generation was running. Process ancestry and the native model catalog identified an idle language-model worker, rather than a dashboard arithmetic error. Its model-specific configuration had no inactivity timeout.

The correction used the runtime's native idle-sleep control for only the selected preset. A supported catalog refresh activated the setting without restarting the manager. Other presets, startup task, launch script, file permissions and context size were preserved. Actual child arguments confirmed activation; a configuration write or catalog acknowledgement alone would have been weaker evidence.

Two natural inactivity windows released the weights and context memory. A real request between them reloaded the model and returned an answer; the second idle window released memory again. The listener remained available, with some residual driver allocation. This trades immediate readiness for a cold reload on the next use and does not free unrelated desktop or image-workflow allocations.

The checks used status endpoints that do not count as inference tasks, measured accelerator memory alongside sleeping status and retained the raw response before assertions. Existing services on the separate assistant host were unchanged. Reboot, long endurance and interruption behavior during a real user's long generation were not tested. Rollback is limited to the owned preset setting at an idle boundary; no model files or conversation history are removed.
