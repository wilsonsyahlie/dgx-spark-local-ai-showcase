# A bounded patch proposal path

A prior instruction-only repair experiment failed its acceptance target. Much faster individual code generations later used a different mechanism: bounded requests without extended reasoning. Those unequal tasks did not establish a workflow speed improvement.

The subsequent implementation separated proposal generation from source mutation. A helper accepts a selected region of a task file and returns strictly validated literal edits, bound to the original and proposed content hashes. It cannot apply source changes or execute generated commands. Existing protected editing tools retain predecessor backups, and normal executable/browser checks remain required. Small understood repairs can select this path; uncertain, stateful or security-sensitive work retains fuller planning. Selection is cooperative guidance rather than a universal enforcement mechanism.

Fourteen focused test groups cover strict parsing, request serialization, size/scope/ambiguity limits, stale input, durable status and uncertain-outcome no replay. A neutral native repair selected the helper without coaching, applied the exact backed edit and passed desktop/phone click, repeated-click and refresh observations. Proposal generation took about two seconds; the complete user-to-final turn took about ninety-nine seconds, including an invalid publishing argument that the creator corrected. No matched timing baseline or general speed gain is established.

Review retained procedural misses: the creator skipped initial current-state publication and did not demonstrate a fresh hash read immediately before applying the patch. The independently checked predecessor proves the intended source was edited in that run. A separate planning-only question selected fuller review for a database/authentication change without executing it. The exact helper request completed durably, while a separate dispatch-time request remained orphaned after a client disconnect. That bookkeeping debt is unresolved and outside this implementation; an idle backend is not proof of durable request closure.

The result is a qualified narrow mechanism with explicit limits, rather than a demonstrated general performance upgrade. Generated proposals still require verification; concurrency against unrelated writers, universal instruction adherence, aesthetic quality and long-running reliability remain outside the observed result. This retrospective contains no deployable procedure or current operational configuration.
