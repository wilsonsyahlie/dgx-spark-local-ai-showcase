# When a performance experiment cannot produce a performance result

A bounded graphical coding rebuild was intended to compare project history with a fresh factual brief. The first attempt stopped after about271seconds without producing an implementation, when a retained resource protection interrupted its backend. The second attempt was not started. No replacement artifact or speed improvement was demonstrated.

The preparation established equal task requirements, empty starting folders, complete effective instructions and tool schemas. It also preserved actual history relationships rather than substituting a displayed transcript. Historical solution code remained naturally available in the history arm, an explicit interpretation limit.

The engineering result was a verified stopping boundary. A successful process exit was distinguished from a failed task, and worker closure was distinguished from backend health. A protection trigger was recorded without claiming to know which process caused the underlying system condition. Existing conversations and configuration were preserved; safeguards were retained.

Verification itself needed correction. A reset check initially proved only that a key caused no runtime error. A no-op mutation exposed that weakness; the corrected check rejected the mutation while preserving the other behavior checks. Visual inspection separately found framing problems in the reference, showing why functional automation alone cannot establish visual quality. A missing early predecessor backup remains an explicit evidence gap.

Request-construction controls do not establish successful streaming, graceful shutdown or completed work. Smaller context does not establish faster delivery. A single ordered pair would also carry cache and history-reuse limits, even if it completed.

The practical lesson is to retain a failed experiment honestly. Restoring availability would not prove the underlying defect fixed, and a blocked comparison cannot support promoting a performance setting.
