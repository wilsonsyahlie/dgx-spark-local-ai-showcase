# Durable predecessors for consecutive local edits

A small repair comparison exposed a reliability failure: both workers changed the same file twice but saved only its initial version. Neither result qualified. More instructions did not make per-edit protection dependable, so the next bounded change enforced it at the supported local write boundary.

Each protected write now captures the actual previous bytes and file metadata, verifies the saved bytes, and makes the receipt durable before replacement. Consecutive edits retain distinct predecessors. Backup or identity failures refuse replacement. If replacement succeeds and a later verification or result-conversion step fails, the response retains the receipt and states that a write occurred. Scope, links, ownership, simultaneous attempts and new-file collisions are checked without relaxing existing syntax or write policy.

Evidence progressed from focused filesystem cases through real file-operation and serialized tool calls, existing regressions, the built artifact, then a native application task. There were 196 passing host checks and four explicit platform skips. The installed artifact passed 39 checks plus consecutive edits at the actual workspace boundary. The native task made two separate patch calls; independent inspection matched both raw predecessors, receipt hashes, actual backup metadata, final bytes and final metadata. Existing conversation rows and profile settings stayed intact. A natural scheduled run after restart produced a durable suppressed receipt with zero delivery attempts and a valid future run.

The first package was rejected for broader file permissions. Test fixtures also initially landed outside the unchanged write boundary because their isolated parent was inaccessible; the correction changed the isolated mount, then checked access before running tests. Two fixture assumptions about existing preflight and conservative no-op behavior were corrected while retaining negative and genuine partial-failure cases. A missed pre-test timing-cache backup remains an explicitly unrecoverable historical gap; it was not relabeled as protected.

Deployment also revealed an independently supervised application entrypoint that did not follow the main restart. The first acceptance attempt created no session and submitted no task. Its failed-unsent record was preserved. After separate review, current-state protection and exact ownership checks, one supported start re-established the unchanged entrypoint; authenticated read-only access and invalid-auth rejection passed before one fresh bounded native task. Container health alone was insufficient evidence of entrypoint readiness.

The activated change improves supported local edit recoverability. Terminal writes, moves and deletes remain outside this protection. Contention is rejected rather than queued; unrelated writers and stale patch computation receive no conflict-merging guarantee. Archive retention is manual. Physical client acceptance, actual untested platforms, long-duration behavior and a general speed improvement were not established. Existing inference, reasoning and service policies were preserved.

Lesson: protect every actual predecessor and carry the receipt through the entire result path. Verify the installed bytes and metadata, inventory independently supervised entrypoints before replacement, and require real user-path evidence after restart.
