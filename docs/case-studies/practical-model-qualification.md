# Practical model comparison needed a trustworthy harness

A promising coding fine-tune was evaluated against an established worker using three small practical jobs: a debugging repair, a scoped change across two files and a dependency-free command-line project. Each job had fixed independent assertions and a write boundary. Model-created files were checked in an isolated offline environment, with backups before replacement.

The established configuration passed all three jobs. An eight-bit candidate loaded its weights but stopped during startup at an unchanged host swap-growth guard; no coding score followed. A smaller four-bit configuration passed two jobs before its project stream lost the client connection. That interruption was an infrastructure result, not evidence that the model could not code. The original error output had not been retained, so its exact cause remained unproven.

## Verification changed before another comparison

Positive and negative controls checked malformed streams, terminal ownership, bounded input/output, durable writes, independent assertions and exact cleanup. An early process exit could not count as a completed checker. Timeout and excess-output checks had to return a bounded failure, preserve evidence and close the exact owned execution. Scaled delayed-stream controls supported aligned connection deadlines without retrospectively proving the earlier failure mechanism.

An optional author-supplied speculative draft was treated as a separate serving configuration. Its declared cache format was reviewed before launch; matching model dimensions alone did not prove runtime compatibility. A measured cache pool was required rather than trusting a declared context limit. Existing resource guards and restoration requirements were retained.

## Completed accelerated comparison

The separately labeled accelerated candidate completed all three practical jobs with independent assertions and scope checks. Its initialized cache pool was measured at the required capacity before dispatch. It was faster on two jobs and slower on one than the established configuration; one run of tiny tasks does not establish a repeatable speed advantage or greater coding capability. The interrupted earlier attempts were preserved rather than rescored.

## Recovery had to be idempotent

The completed accelerated comparison exposed a repeat-cleanup defect: a temporary worker had already been collected, so stopping its missing service halted restoration. Recovery was reviewed separately and required the exact prior closure, a freshly verified stopped execution, an empty owned process group and positive service absence. Unknown state and failures stopping an existing service remained fatal. Positive and negative controls qualified this narrow recovery path without replaying the completed coding jobs.

## Limits

Three small jobs do not establish overall superiority, long-context reliability or a production replacement. Timing differences also include serving configuration and acceleration, so they cannot be attributed solely to model weights. Startup failures, transport failures and failed harness controls remain visible alongside successful coding checks. A comparison must distinguish downloaded artifacts, runtime execution, coding quality and deployment qualification.
